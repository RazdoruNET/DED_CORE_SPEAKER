# Серийная плата: что обязательно сделать перед производством

Прототип хранит ключ устройства и пароль Wi-Fi в NVS открытым текстом. Пока
человек не имеет физического доступа к плате, это не проблема; после первой
поставки — проблема: UART и чтение флеша дают ключ, а ключ — доступ к колонке
и её настройкам. Здесь — минимальный набор требований, без которых партию
выпускать нельзя.

## Что защищаем

| Секрет | Где лежит | Цена утечки |
|---|---|---|
| ключ устройства (`deviceKey`) | NVS, `spk_cfg/device_key` | подключение к серверу от имени колонки |
| пароль Wi-Fi | NVS, `spk_cfg/wifi_pass` | доступ в домашнюю сеть |
| код с наклейки | NVS, `spk_id/code` | возможность привязать колонку к чужому аккаунту |
| ключ подписи grant | только на сервере (Vault) | в прошивку не попадает никогда |

## Обязательные меры

1. **Flash encryption (AES-XTS)** — включает шифрование всей флеш-памяти,
   включая NVS. Ключ шифрования хранится в eFuse и недоступен через UART.
2. **Secure boot v2** — загрузчик проверяет подпись приложения. Без него
   шифрование защищает только от чтения, но не от подмены прошивки.
3. **Запрет UART-загрузки в серии** (опционально, по модели угроз): после
   прожига eFuse `UART_DOWNLOAD_DIS` прошивка возможна только через OTA.
4. **Сборка `esp32s3_prod`** — в ней включён `SPEAKER_REQUIRE_SECURE_FLASH`:
   на старте проверяется `esp_flash_encryption_enabled()`, и без шифрования
   колонка не открывает привязку и не поднимает сеть (лента — красная ошибка,
   в лог одна строка). Это защита от «на плате забыли прожиг eFuse».
5. **Код привязки в NVS** — пишется при производстве в `spk_id/code`
   (каноническая форма: заглавные A-Z и 0-9). С прошитым кодом устройство
   принимает только кадр привязки версии 2: ключ шифрования настроек выводится
   с участием кода, поэтому подставное BLE-устройство без кода не прочитает
   пароль Wi-Fi. Без кода (кадр версии 1) этот риск остаётся — такие устройства
   допустимы только как макет.

## Порядок производства

1. Собрать образ из `esp32s3_prod` (или из `esp32s3` с тем же флагом).
2. Записать код привязки и, если нужно, серийные данные в NVS до включения
   шифрования (после — только через OTA/шифрованный порт).
3. Прожечь eFuse: flash encryption + secure boot v2 (development mode на первой
   партии, production mode — после отладки). **Прожиг необратим.**
4. Первая загрузка в режиме разработки шифрует образ на месте; проверить в
   логе, что `[security]` не срабатывает, а `[crypto] код привязки прошит`.
5. Проверить, что чтение флеша внешним программатором даёт нечитаемый дамп, а
   привязка идёт кадром версии 2 (`info.frame = 2`).
6. Для каждой колонки — запись в базе платформы: `deviceId`, хеш кода
   привязки, `product = smart-speaker`. Отпечаток открытого ключа закрепится
   сам при первой привязке.

## Что делать при утечке

* **Ключ устройства**: «Отвязать» или «Колонка украдена» в профиле —
  `report-stolen` блокирует устройство навсегда, `unbind` освобождает его для
  нового владельца. Ключ после этого не принимается.
* **Пароль Wi-Fi**: смена пароля в роутере; колонка перестаёт подключаться.
  После сброса кнопкой (10 с) NVS стирается, нужна новая привязка.
* **Код с наклейки**: колонку нужно перепривязать с новым кодом, выданным
  при производстве; старый код в базе помечается недействительным.

## Что остаётся за рамками прошивки

* производственная база кодов и их печать (наклейка + QR `DED1:<id>:<code>`);
* хранение ключа подписи grant в Vault и ротация;
* проверка партии: сколько устройств реально ушло в продажу.

Эти пункты — часть производственного процесса, а не кода в этом репозитории.
Пока их нет, устройство остаётся макетом: см. «Остаточные риски» в
[`07-pairing-security.md`](./07-pairing-security.md).
