# Архитектура

## Слои

```
┌──────────────────────────── колонка (ESP32) ────────────────────────────┐
│  аудиотракт        арбитр звука      локальные умения      шлюз          │
│  I2S mic → VAD     кто владеет       таймеры, будильники   ESP-NOW       │
│  wake word         микрофоном и      громкость, ИК, BT     Zigbee (H2)   │
│  Opus enc/dec      динамиком         локальные сценарии    MQTT          │
└───────────────────────────────────┬─────────────────────────────────────┘
                                    │ бинарный WebSocket (WSS)
┌───────────────────────────────────┴─────────────────────────────────────┐
│                          AssistantService                                │
│  SpeakerGateway ── STT ── быстрый разбор / AgentRuntime ── TTS ── Opus    │
│                     │            инструменты            │                │
│                     └──── HomeDeviceService / Audit ────┘                │
└───────────────────────────────────┬─────────────────────────────────────┘
                                    │
              FirmwareService (OTA, ключи) · IdentityService (привязка)
```

Колонка никогда не содержит бизнес-логику платформы. Всё, что требует знания
пользователя (что такое «спальня», какой у него тариф, что он вчера спрашивал),
живёт на сервере. В колонке — только то, что нужно для работы **в отсутствие**
сервера.

## Три режима и арбитр звука

Один физический тракт обслуживает несколько сценариев, которые не должны
перебивать друг друга. Арбитр (`AudioArbiter` в прошивке) держит ровно одного
владельца микрофона и одного владельца динамика.

| Владелец | Приоритет | Микрофон | Динамик |
|---|---|---|---|
| Интерком (звонок с сайта/другой колонки) | 100 | занят | занят |
| Сессия сайта (человек за компьютером) | 80 | занят, если запрошен | занят |
| Агент (колонка сама вызвала сервер) | 60 | занят | занят |
| Автономный (локальные команды, ИК, BT) | 40 | занят по wake word | свободен |
| Будильник / таймер | 90 | свободен | занят |
| Медиа (радио, музыка) | 20 | свободен | занят, если выше нет |

Правила:

* старший владелец **вытесняет** младшего (интерком прерывает музыку);
* младший не может вытеснить старшего, но может попросить (событие `preempt.request`);
* будильник вытесняет всё, кроме интеркома;
* сессия сайта отпускает звук сама через 30 с бездействия или по событию `session.end`;
* после освобождения динамика возобновляется то, что было приглушено (музыка), но не то,
  что было прервано (недосказанный ответ агента).

## Автономный режим: что именно работает без сервера

Сервер недоступен (нет сети, упал `AssistantService`, выключен домашний мини-сервер):

| Умеет | Как |
|---|---|
| Wake word | локально (MicroWakeWord), от сервера не зависит |
| Набор команд «умный дом» | локальный KWS: 20–30 фраз, привязанных к ИК-кодам и ESP-NOW-устройствам |
| Таймеры и будильники | полностью локально, RTC + NTP при появлении сети |
| Громкость, mute, «стоп» | всегда, в любом режиме |
| ИК-пульт | локальные сценарии «кондиционер 23°» без сети вообще |
| Bluetooth-приёмник | ESP32 A2DP sink, воспроизведение с телефона |
| Локальные сценарии | «свет в коридоре по датчику движения» — правила лежат в NVS, приходят с сервера при связи |

Чего **не** бывает без сервера: свободный диалог, ответы на вопросы, доступ к
платформе, история разговоров. На это колонка честно отвечает голосом
«нет связи с сервером» — заранее синтезированной фразой из кэша
(`/voice/cache/offline.opus` на флеше), а не тишиной.

Локальные сценарии приходят с сервера и версионируются:
`GET /api/assistant/speaker/{id}/rules` → `{version, rules[]}`. Колонка хранит
последнюю версию в NVS и работает по ней, пока не получит новую. Так сервер
остаётся единственным источником правды, но его недоступность ничего не ломает.

## Режим «сессия сайта»

Когда человек за компьютером, открытая вкладка уже держит потоковый STT
(Web Speech API), агента и `speechChunk`. Второй разговор в колонке не нужен —
нужен звук в комнате.

```
браузер ──WS /api/assistanthub── AssistantService
   │  speaker.attach(deviceId)
   │                                     │ CMD(session.attach)
   └────────────── колонка ◄─────────────┘
        mic → браузер (опционально, кнопка «говорить в колонку»)
        speechChunk → колонка говорит
```

* `speaker.attach` — выбор колонки в настройках Лиры на сайте (список приходит из
  `GET /api/assistant/speaker/devices`);
* в этом режиме сервер дублирует `speechChunk` на устройство, браузер **не**
  проигрывает звук сам (`audio.muted = true`), колонка играет;
* микрофон колонки может быть подключён к браузерной сессии (кнопка «говорить
  отсюда») — тогда распознавание идёт тем же путём, что с телефона;
* сессия умирает при закрытии вкладки: сервер посылает `session.end`, колонка
  отпускает звук.

## Интерком

Двусторонний звук между сайтом (или другой колонкой) и этой колонкой.

* вызов: `POST /api/assistant/speaker/{id}/intercom` — сервер открывает
  двунаправленный поток `streamId`, колонка звонит (тон + LED);
* разговор полудуплекс на ESP32 classic (нет AEC): кто говорит, тот и держит
  канал; переключение по VAD или кнопке;
* на ESP32-S3 с AFE — полный дуплекс;
* таймаут 60 с без звука закрывает вызов.

## Хаб: как колонка собирает устройства
| Транспорт | Что подключается | Как попадает на платформу |
|---|---|---|
| ESP-NOW | батарейные датчики (дверь, движение, SHT40) | колонка публикует `sensor` события в WS, сервер пишет в `HomeDevices` |
| UART (ESP32-H2) | Zigbee/Thread-устройства | колонка = шлюз, сервер видит их через будущий `zigbee`-провайдер |
| ИК | ТВ, кондиционер, вентилятор | колонка хранит коды, сервер шлёт `CMD(ir.send, {code})` |
| BLE | термометры, весы, браслеты | периодический опрос, события в WS |
| MQTT (напрямую в брокер) | всё остальное | колонка — мост, если брокер локальный |

Ключевая мысль: колонка **не** строит свою модель умного дома. Она пересылает
события и команды. Единственный источник правды — `HomeDevices` на сервере.

## Отказоустойчивость

| Отказ | Поведение |
|---|---|
| пропал Wi-Fi | повтор с backoff (5 с → 5 мин), локальные умения работают, LED жёлтый |
| сервер отвечает 5xx | 3 попытки, затем автономный режим на 60 с, потом снова |
| WS завис (TCP жив, данных нет) | ping каждые 15 с, нет pong 2 раза → реконнект |
| питание пропало | состояние (громкость, будильники, правила) в NVS, поднимается за 3 с |
| перегрев | при > 75 °C на кристалле — снижение до 160 МГц, в лог и в телеметрию |
| OTA сорвалась | два слота + откат по `otadata`, проверка SHA-256 образа |

## Настройка: только Bluetooth

Точки доступа и веб-страницы на устройстве нет. Настройка идёт из браузера
(Web Bluetooth) или мобильного приложения: сайт находит колонку по сервису,
читает открытый ключ, шифрует Wi-Fi и токен привязки, пишет кадр — колонка
применяет и перезагружается. BLE живым остаётся только в окне привязки
(первое включение, удержание кнопки 5 с) и гаснет навсегда после успеха.

Почему не точка доступа: страница настройки на устройстве — это поверхность
атаки (чужой в радиусе), 1 МБ флеша и лишний код. Полная механика и модель
угроз — [`07-pairing-security.md`](./07-pairing-security.md).

## Свет как состояние

Лента WS2812 кодирует фазу агента цветом и движением
(см. таблицу в [README](../README.md#свет-как-язык-агента)). Она же — главный
индикатор приватности: выключенный микрофон перекрывает любое состояние красным.
В прошивке это отдельный модуль `app/Ui.cpp`, который не блокирует задачи:
все анимации на `millis()`, ни одного `delay()`.

## Почему бинарный WS, а не SignalR и не HTTP

* SignalR на ESP32 — это JSON-конверт на каждый кадр и полная реализация протокола
  (negotiation, handshake, keepalive) на 520 КБ SRAM. Кадр 20 мс Opus = 60 байт
  полезных данных; JSON-обёртка вокруг него — 120+ байт служебных.
* HTTP-запрос на каждую фразу (multipart) не даёт barge-in: пока сервер
  синтезирует, колонка не может ни прервать, ни услышать «стоп».
* Голый бинарный WS: 2 байта заголовка, один долгоживущий сокет, дуплекс,
  управляемый размер буферов. Формат — в [`02-audio-protocol.md`](./02-audio-protocol.md).
