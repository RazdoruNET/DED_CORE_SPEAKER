# Протокол связи колонки с сервером

Звук по Bluetooth **не ходит**: BLE используется только для первой привязки
([`07-pairing-security.md`](./07-pairing-security.md)), потому что его пропускной
способности не хватает даже на один Opus-поток в обе стороны и он не переживает
выход из комнаты.

Транспорт — один долгоживущий **бинарный WebSocket** на устройство:
`wss://<api>/api/assistant/speaker/stream`. Устройство сначала устанавливает
проверенный TLS-канал, затем отправляет `HELLO` первым бинарным сообщением.
Ключ и одноразовый токен запрещено передавать в URL или HTTP-заголовках.
Сервер должен закрыть соединение, если корректный `HELLO` не пришёл за 5 секунд.

## Кадр

```
 0        1        2        3        4        5        6
+--------+--------+--------+--------+--------+--------+--------- - - -
|  type  | flags  |  streamId (u16 LE)  |  seq (u16 LE)   |  payload
+--------+--------+--------+--------+--------+--------+--------- - - -
```

* заголовок 6 байт, payload до 1200 байт (`MTU 1280` за вычетом TLS/WS);
* `streamId` различает параллельные потоки (ответ агента, интерком, медиа);
  `0` — служебный;
* `seq` — счётчик внутри потока, по нему отбрасывается переупорядоченное и
  считается потеря кадров;
* `flags` — биты: `0x01` начало потока, `0x02` конец потока, `0x04` повтор,
  `0x08` mark (для VAD/прерывания).

JSON в payload — только для управляющих кадров, никогда для звука.

## Типы кадров

| Код | Имя | Направление | Payload |
|---|---|---|---|
| `0x01` | `HELLO` | ↑ | JSON: ключ, версия прошивки, железо, возможности |
| `0x81` | `HELLO_ACK` | ↓ | JSON: пользователь, кодек, кадр, битрейт, голос, heartbeat |
| `0x02` | `MIC` | ↑ | Opus-кадр микрофона |
| `0x03` | `SAY` | ↓ | Opus-кадр речи Лиры |
| `0x04` | `SPEECH_BEGIN` | ↓ | JSON: `{streamId, text?}` |
| `0x05` | `SPEECH_END` | ↓ | JSON: `{streamId, truncated}` |
| `0x06` | `VAD` | ↑ | JSON: `{event: start\|end, rms, ms}` |
| `0x07` | `CONTROL` | ↕ | JSON: `stop`, `barge_in`, `ping`, `pong`, `ack` |
| `0x08` | `STATE` | ↑ | JSON: громкость, mute, датчики, RSSI, heap, uptime |
| `0x09` | `EVENT` | ↑ | JSON: `wake`, `button`, `timer`, `sensor`, `error` |
| `0x0A` | `CMD` | ↓ | JSON: `say`, `led`, `volume`, `ir.send`, `rules.update`, `session.*`, `intercom.*`, `ota` |
| `0x0B` | `CODEC` | ↓ | JSON: `{codec, rate, frameMs, bitrate}` |
| `0x0C` | `INTERCOM` | ↕ | Opus-кадр разговора |

## Рукопожатие

```
устройство                              сервер
    │  HELLO {deviceKey|token, pub,       │
    │         fw, hw, muted, caps}        │  проверка ключа (хеш в базе)
    ├─────────────────────────────────────►│  для токена: сверка pub
    │                                      │  с отпечатком привязки
    │  ◄──── HELLO_ACK {userId, voiceId,   │
    │         heartbeatSec, rulesVersion,  │
    │         serverTime}                  │
    │  ◄──── CODEC {opus, 16000, 20, 24000}│
    │  ◄──── CMD {rules.update} (если нужно)│
    │                                      │
    │  ◄════ SAY / CMD ════════════════════│  дальше только кадры
```

Если ключ не принят — `CONTROL {error: "unauthorized"}` и закрытие с кодом
`4401`. Повторная попытка не раньше чем через 30 с с backoff до 5 мин.
Сертификат сервера проверяется по CA, встроенному в локальный
`firmware/src/config/Secrets.h`; если CA отсутствует, соединение даже не
начинается. `ws://` и insecure TLS не поддерживаются.

Два поля `HELLO` несут безопасность, а не диагностику:

* `pub` — открытый ключ устройства (несжатая точка P-256, 130 hex). При входе
  по одноразовому токену сервер сверяет `SHA-256(pub)` с отпечатком из записи
  привязки и только потом выдаёт `deviceKey`: перехваченный BLE-кадр с токеном
  не даёт чужому устройству стать этой колонкой;
* `muted` — микрофон выключен. Пока он `true`, сервер не накапливает кадры
  `MIC` и не запускает распознавание. Прошивка в этом состоянии кадры не шлёт
  вовсе, но проверка на сервере остаётся: «микрофон выключен» — обещание
  человеку, и оно не должно зависеть от версии прошивки на устройстве.
  Переключение по кнопке приходит событием `EVENT {kind: muted|unmuted}`.

## Звук

| Параметр | Значение | Почему |
|---|---|---|
| кодек | Opus, CELT+SILK, 16 кГц, моно | речь, декод на классическом ESP32 ~15–20 МГц |
| кадр | 20 мс (320 сэмплов) | баланс задержки и накладных расходов |
| битрейт | 24 кбит/с вверх, 24 кбит/с вниз | 3 КБ/с вместо 32 КБ/с у PCM16 |
| сложность кодера | 0–2 | на 520 КБ SRAM и 240 МГц выше не имеет смысла |
| FEC | включён вниз, выключен вверх | потери вниз слышны, вверх — переспросим |

Сервер кодирует **тот же Opus для всех колонок** и кеширует результат по
`hash(фраза + голос + параметры кодека)`: у платформы уже есть кеш синтеза, к
нему добавляется вторая ступень «mp3 → opus». Один и тот же ответ на все колонки
синтезируется один раз.

## Бюджет задержки (wake → первый звук)

| Этап | Бюджет | Как достигается |
|---|---|---|
| VAD + end-of-speech | 500 мс | 400 мс тишины + подтверждение по энергии |
| подъём кадра до сервера | 50 мс | один WS, без новые соединений |
| STT (стриминговый) | 300 мс | партиалы sherpa-onnx, а не whisper на всю фразу |
| старт агента | 200 мс | по стабильному партиалу; быстрый разбор перехватывает команды |
| первый чанк TTS | 300 мс | `LiveSpeechStream` уже делит по фразам |
| mp3 → opus + дорога вниз | 150 мс | кеш + 2 кадра буфера |
| **итого** | **≤ 1.5 с** | |

Сейчас в платформе на этом пути 5–7 с: VAD 900 мс, whisper на всю фразу (~3 с на
четырёх ядрах), потом модель. Колонка без стримингового STT получится
«задумчивой» — это первое, что надо починить на сервере
([`03-server-plan.md`](./03-server-plan.md)).

## Barge-in и эхо

ESP32 classic не имеет аппаратного AEC (AFE в esp-sr 2.x — только S3+PSRAM).
Поэтому:

1. **слова-перебивки** (`стоп`, `замолчи`, `хватит`) распознаются локальным KWS
   даже во время речи; на них динамик глушится в ту же миллисекунду, поток
   закрывается кадром `CONTROL {barge_in}`, сервер снимает запуск;
2. **wake word во время речи** — то же самое (второй вопрос без «стоп»);
3. пока колонка говорит, обычный VAD **не** открывает микрофонный поток
   (полудуплекс) — иначе сервер получает собственный голос Лиры;
4. на S3 включается AFE с AEC, и правило 3 снимается — полный дуплекс.

Защита от самопрослушивания на сервере (аналог браузерной) не нужна: полудуплекс
исключает петлю физически.

## Устойчивость канала

* `ping` каждые 15 с, два пропущенных `pong` — реконнект;
* при потере 3 кадров подряд вниз поток прекращается, колонка просит `SPEECH_BEGIN`
  заново (сервер отдаёт с начала фразы, а не с начала ответа — буфер фразы живёт 60 с);
* при реконнекте `HELLO` несёт `lastStreamId`, незавершённый поток закрывается
  событием `SPEECH_END {truncated: true}`, и колонка не повторяет оборванную фразу;
* джиттер-буфер вниз — 3 кадра (60 мс); при недоборе играет тишину, а не рвёт звук.

## Резервный путь по HTTP

Если WS не поднимается (корпоративный прокси, старый Wi-Fi), колонка работает
урезанно, но работает:

| Метод | Ручка | Назначение |
|---|---|---|
| POST | `/api/assistant/speaker/{id}/utterance` | тело `audio/opus`, ответ `{text, streamId, replyOpusUrl}` |
| GET | `/api/assistant/speaker/{id}/speech/{streamId}/{n}` | готовый Opus-чанк, кешируется |

Это же используется на этапе 1 прототипа: проще отладить тракт, когда ответ
приходит целиком.

## MQTT (режим хаба)

Колонка публикует и подписывается, если в конфигурации задан брокер:

```
ded/speaker/{deviceId}/state      ↑ {volume, mute, online, rssi}
ded/speaker/{deviceId}/sensor     ↑ {kind, value, unit, ts}
ded/speaker/{deviceId}/event      ↑ {kind, payload}
ded/speaker/{deviceId}/cmd        ↓ {action, args}      ← от сервера и от сценариев
ded/speaker/{deviceId}/ir         ↓ {protocol, code}
```

Топики стабильные: их будут использовать автоматизации, а не только сервис.

## Коды ошибок

| Код | Смысл | Что делает колонка |
|---|---|---|
| `4401` | ключ не принят | не переподключается, LED красный, просит привязку |
| `4403` | устройство чужого пользователя | то же |
| `4426` | прошивка устарела (принудительно) | запускает OTA |
| `4503` | сервис перегружен | backoff 60 с, автономный режим |
| `4000` | обычное закрытие (сервер перезапустился) | реконнект через 2 с |
