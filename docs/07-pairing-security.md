# Первая синхронизация колонки и учётной записи

Самое опасное место во всём устройстве. Колонка — это микрофон в квартире и
пульт управления домом. Ошибка здесь означает не «неудобно», а «чужой человек
слушает ваш дом». Поэтому привязка строится на трёх независимых якорях доверия,
а не на одном.

## Что защищаем

| Что | Цена ошибки |
|---|---|
| пароль Wi-Fi пользователя | доступ в домашнюю сеть |
| право управлять колонкой голосом | подслушивание, команды устройствам |
| доступ к платформе от имени пользователя | личные данные, публикации, оплата |
| сама колонка как имущество | кража и перепривязка к вору |

## Модель угроз

| # | Атакующий | Что пытается |
|---|---|---|
| A | сосед с телефоном в радиусе BLE | привязать колонку к своему аккаунту |
| B | пассивный перехватчик эфира | прочитать Wi-Fi пароль из BLE |
| C | подставное BLE-устройство | выдать себя за колонку и получить Wi-Fi пароль сайта |
| D | подставной сайт/сервер | выдать себя за платформу и завладеть колонкой |
| E | вор, укравший колонку | привязать к себе, читать NVS |
| F | бывший жилец, знавший прежний пароль Wi-Fi | вернуть себе доступ |
| G | запись голоса владельца | отдать команду «открой замок» |

## Три якоря доверия

1. **Код на наклейке** — индивидуальный секрет устройства, печатается при
   производстве и хранится в базе платформы. Единственный признак физического
   владения.
2. **Ключ устройства P-256** — генерируется на первом включении и живёт в NVS.
   По нему колонка доказывает серверу, что она — это она, и по нему сайт
   шифрует настройки.
3. **Сервер** — единственная сторона, которая связывает код и колонку. Ни
   колонка, ни сайт не решают сами, чья это вещь.

Ни один из трёх не достаточен в одиночку: код можно сфотографировать, ключ можно
вычитать из флеша, сервер можно подменить. Вместе они закрывают всю таблицу.

## Поток привязки

```
пользователь        сайт (Chrome/Edge)          сервер            колонка
     │   код с наклейки  │                        │                  │
     │  выбор колонки    │                        │                  │
     │  в списке BLE     │                        │                  │
     │                   │ ──── BLE: info ───────────────────────────►│
     │                   │ ◄── {id, pub, challenge, frame, fw} ────────┤
     ├──────────────────►│  pair/claim {code, id, pub, challenge}    │
     │                   ├───────────────────────►│ создаёт pairToken│
     │                   │  ◄── {signed grant} ───┤ (10 мин, однораз.)│
     │                   │  проверяет grant, ECDH + HKDF + AES-GCM  │
     │                   │ ──── BLE: pair (кадр) ────────────────────►│
     │                   │ ◄─── {stage: paired} ─────────────────────┤
     │                   │                        │   ◄── HELLO {token, pub}
     │                   │                        ├── сверка pub и токена
     │                   │                        ├── token → deviceKey
     │                   │                        │   закрепление отпечатка
     │                   │                        │   ── HELLO_ACK ──►│
```

Пошагово:

1. Пользователь: профиль → «ИИ Агент» → «Добавить колонку» → вводит 12 символов
   с наклейки либо сканирует QR `DED1:<deviceId>:<code>`. Этот код должен быть
   заранее создан и зарегистрирован сервером при производстве устройства.
2. Сайт открывает выбор BLE-устройства (`navigator.bluetooth.requestDevice` с
   фильтром **только по UUID сервиса**), пользователь тыкает в колонку.
   Фильтровать по имени нельзя: 128-битный UUID съедает 18 из 31 байта
   рекламного пакета, имя обрезается, а macOS ещё и показывает закэшированное
   имя от прежней прошивки устройства. Проверено на железе: в эфире
   `local_name = DED-SPK-F904`, а система отдаёт «DED CORE» — имя прежней
   прошивки этого модуля.
3. Сайт читает характеристику `info` (`deviceId`, открытый ключ и случайный
   128-битный challenge текущего окна) и отправляет их вместе с кодом:
   `POST /api/assistant/speaker/pair/claim {code, deviceId, publicKey, challenge}`.
4. Сервер находит устройство по хешу производственного кода, проверяет, что оно
   свободно, создаёт одноразовый `pairToken` (TTL 10 минут) и возвращает grant.
5. Сервер подписывает grant ключом ES256, закрытый ключ хранится только на
   сервере в Vault. Подписываются строго канонические UTF-8 байты:

   ```
   DED-CORE-SPEAKER-PAIR-V1\n
   {deviceId}\n
   {lowercase hex SHA-256(devicePublicKey)}\n
   {challenge из BLE info}\n
   {userId}\n
   {pairToken}\n
   {apiBase}
   ```

   ECDSA-подпись передаётся как DER (`Rfc3279DerSequence`) в стандартном
   Base64. Firmware проверяет подпись по закреплённому `SPEAKER_PAIRING_PUBLIC_KEY_HEX`
   (несжатая точка P-256 в hex: в предсборке mbedTLS разбор PEM может быть
   выключен).
   Подписанный grant привязывает выдачу к конкретным `deviceId`, открытому ключу
   и свежему challenge. Подставное BLE-устройство со своим ключом не сможет
   принять токен на настоящей колонке: firmware сверит fingerprint с собственным
   ключом до применения настроек.
6. Сайт генерирует эфемерную пару P-256, считает ECDH с ключом колонки и
   выводит ключ шифрования через HKDF:
   `salt = SHA-256(devicePublic || ephemeralPublic)`,
   `info = "ded-speaker-pair-v2" || 0x0A || code` — если колонка сообщила
   `frame: 2` в BLE `info`; `info = "ded-speaker-pair-v1"` — если `frame: 1`.
   Код в `info` берётся в канонической форме (заглавные A-Z и 0-9). Дальше —
   AES-256-GCM на полезную нагрузку:
   `{ssid, pass, api, name, room, grant:{deviceId, publicKeySha256, challenge,
   userId, pairToken, apiBase, signature}}`.
   Благодаря коду подставное BLE-устройство, не знающее наклейку, выведет
   другой ключ и прочитает только шифртекст.
7. Кадр пишется в характеристику `pair` кусками по 240 байт:
   `[u16 длина][u16 смещение][данные]`.
8. Колонка расшифровывает данные, проверяет свежий challenge, идентификатор,
   fingerprint ключа и подпись сервера, сверяет подписанный `apiBase` с
   конфигурацией. Только затем сохраняет сеть и токен, отвечает
   `{stage: "paired"}`,
   гасит BLE и перезагружается — чтобы не осталось полуприменённого состояния.
9. Колонка поднимает WSS с проверкой CA и отправляет `HELLO {token, pub}`.
   Сервер сверяет `SHA-256(pub)` с отпечатком, для которого выпущен токен,
   **атомарно** обменивает одноразовый токен на долговременный `deviceKey`
   (`UPDATE ... WHERE token = ? AND used_at IS NULL`) и отвечает
   `HELLO_ACK {deviceKey, userId}`. Отпечаток ключа закрепляется за устройством
   именно здесь: до этого момента сервер не может знать, что ключ из эфира
   принадлежит настоящей колонке. Колонка сохраняет ключ, токен стирает.

С этого момента BLE не нужен никогда: он выключен до следующего сброса.

## Почему это закрывает модель угроз

| # | Атака | Что её ломает |
|---|---|---|
| A | привязка «с улицы» | окно BLE открыто только по действию человека (первое включение, удержание кнопки 5 с) и закрывается через 5 минут; без кода с наклейки сервер не выдаст `pairToken` |
| B | перехват эфира | Wi-Fi пароль не идёт открытым текстом: AES-256-GCM на ключе, выведенном из ECDH |
| C | подставная колонка | на повторной привязке сервер сверяет ключ из эфира с закреплённым отпечатком; на первой привязке отпечаток закрепляется только после того, как колонка подключится по WSS и предъявит в `HELLO` тот же ключ, поэтому чужое устройство не может ни забрать токен, ни занять устройство навсегда. Остаточный риск первой привязки — ниже |
| D | подставной сервер | колонка принимает настройки только с валидным `pairToken` из своей базы; `deviceKey` выдаётся лишь по нему, а WSS-адрес и TLS-сертификат проверяются |
| E | кража | перепривязка к другому аккаунту требует кода с наклейки **и** карантина с уведомлением прежнего владельца (см. ниже); NVS с ключом на серийной плате закрывается flash-шифрованием |
| F | прежний жилец | старый пароль Wi-Fi бесполезен: он не даёт ни `pairToken`, ни `deviceKey`; доступ к колонке — только через аккаунт владельца |
| G | запись голоса | опасные действия (замки, ворота, сигнализация) голосом не подтверждаются вообще — только в приложении |

## Повторная привязка и продажа

Привязка — это запись на сервере, а не состояние колонки. Колонка не может
«отвязаться» сама: иначе вор сбрасывает её и привязывает к себе.

| Сценарий | Что происходит |
|---|---|
| владелец меняет колонку | «Отвязать» в профиле — сразу, без карантина |
| владелец продаёт колонку | отвязывает сам, покупатель привязывает кодом с наклейки |
| колонка потеряна/украдена | владелец жмёт «Это не я» → блокировка, устройство не принимает команды |
| новый владелец без доступа к аккаунту | код с наклейки → карантин 7 дней + уведомление прежнему владельцу; молчание 7 дней = согласие |

Сброс кнопкой (удержание 10 с) стирает NVS и ключ. Сервер при следующем
подключении видит незнакомый ключ и **не** отдаёт данные — устройство просто
перестаёт работать до новой привязки. Прежний владелец получает уведомление
«колонка сброшена».

## Ограничения, о которых надо сказать вслух

* **Just Works в BLE.** Полноценное BLE-спаривание с числовым сравнением требует
  экрана, которого у колонки нет. Поэтому BLE-линк не считается доверенным:
  конфиденциальность даёт наш собственный ECDH, а аутентичность — `pairToken`
  от сервера. MITM может помешать (DoS), а на **первой** привязке — подсунуть
  своё устройство вместо колонки: от этого защищают короткое окно по кнопке,
  сверка `pub` при обмене токена и внимательность человека при выборе колонки
  в списке (подробнее — «Остаточные риски»).
* **Повтор кадра.** Записанный кадр привязки можно повторить, но окно закрыто
  после успеха, а `pairToken` внутри уже потрачен — сервер второй раз его не
  примет.
* **Наклейку можно сфотографировать.** Поэтому код 12 символов (≈60 бит), лимит
  попыток (5 в час на пользователя, 10 в час на код) и уведомление владельцу о
  каждой попытке привязки его устройства.
* **NVS на прототипе не шифрован.** Ключ устройства и пароль Wi-Fi можно
  вычитать, имея физический доступ и UART. На серийной плате обязательны
  flash encryption и secure boot — это отдельный пункт производства, не
  «когда-нибудь».
* **Web Bluetooth не работает в iOS Safari.** На iOS привязка идёт через
  мобильное приложение (Capacitor + BLE-плагин). Это ограничение платформы, а не
  наше; на сайте показываем «откройте приложение».

## Что нужно от сервера

Реализовано в `AssistantService` платформы; в публичном репозитории колонки эти
файлы не публикуются — здесь описан контракт.

| Элемент | Где |
|---|---|
| `POST /api/assistant/speaker/pair/claim` | `SpeakerController` |
| `POST /api/assistant/speaker/{id}/unbind` | там же |
| `POST /api/assistant/speaker/{id}/report-stolen` | там же |
| таблица `SpeakerPairings` | `deviceId`, `codeHash`, `userId`, `tokenHash`, `createdAt`, `expiresAt`, `usedAt` |
| атомарный обмен токена на ключ | в `SpeakerGateway` при `HELLO`, один `UPDATE ... WHERE used_at IS NULL` |
| лимиты и аудит | `AssistantAuditEntries` + счётчик попыток по коду и по IP |

Код и токен хранятся **только хешами** (SHA-256 с солью устройства): утечка базы
не должна давать возможности привязать чужую колонку.

## Текущее состояние реализации

Реализованы обе стороны: прошивка (ключ P-256, GATT-характеристики, обмен
зашифрованным кадром, проверка подписи grant, криптосамопроверка) и сервер
(`pair/claim`, `devices`, `unbind`, `report-stolen`, `rename`, обмен токена на
`deviceKey`, WebSocket `/api/assistant/speaker/stream`). Границы:

* окно BLE открывается только после удержания физической кнопки 5 секунд;
  автоматической рекламы при старте нет (стендовые `*_bench` сборки — только
  для макета);
* уже сопряжённая колонка не принимает повторную привязку по BLE — сначала
  требуется отвязка в профиле на сайте;
* отпечаток ключа закрепляется при обмене токена на WSS, а не в момент claim:
  прерванная или подставная привязка не занимает устройство навсегда;
* соединение WSS требует доверенный CA из локального `config/Secrets.h`;
  без него прошивка отказывается от TLS, а не переходит в insecure-режим;
* пока не задан `SPEAKER_PAIRING_PUBLIC_KEY_HEX`, прошивка не принимает ни один
  кадр привязки — это безопасный отказ, а не временное отключение проверки;
* прошивка, собранная до появления поля `pub` в `HELLO`, не сможет обменять
  `pairToken` на `deviceKey`: такое устройство нужно привязать заново;
* пока не задан доверенный CA, колонка не подключается к серверу вообще.

## Версии кадра привязки

Версию диктует колонка: она сообщает её полем `frame` в BLE `info`, и кадр
другой версии отвергает. Иначе подменяющее BLE-устройство могло бы «откатить»
схему к варианту без кода.

| Версия | Когда | Ключ кадра | Что защищает |
|---|---|---|---|
| 1 | код с наклейки в устройство не прошит (макет) | HKDF(salt, ECDH, `"ded-speaker-pair-v1"`) | только от пассивного перехвата |
| 2 | код прошит в NVS (`spk_id/code`) | HKDF(salt, ECDH, `"ded-speaker-pair-v2"`,`\n`, код) | и от подставного BLE-устройства |

Серийные устройства обязаны работать версией 2 — это пункт производства
([`09-production-security.md`](./09-production-security.md)). Формула вывода
ключа закреплена эталонными векторами в
[`tools/pairing-kdf-check.py`](../tools/pairing-kdf-check.py): прошивка, сайт и
стендовый `pair.py` обязаны давать одинаковый ключ, иначе привязка ломается
«без причины».

## Остаточные риски

Их нужно назвать вслух — они не закрыты кодом, и в публичном репозитории о них
напишут первым делом.

* **Первая привязка на устройстве без кода (кадр версии 1) — TOFU.** Сервер
  впервые видит открытый ключ из BLE, когда человек вводит код с наклейки.
  Подставное BLE-устройство, выбранное в списке *вместо* настоящей колонки,
  получит зашифрованный кадр и прочитает Wi-Fi пароль. На устройстве с прошитым
  кодом (версия 2) этого не происходит: ключ выводится с участием кода, которого
  у подставного устройства нет. Закрепление отпечатка происходит только после
  WSS-подключения, поэтому «занять» устройство навсегда нельзя и в версии 1.
* **Код с наклейки** хранится на сервере как `SHA-256(deviceId:code)` без
  серверного «перца»: утечка базы позволяет офлайн-перебор, поэтому код обязан
  быть не короче 60 бит случайности.
* **NVS прототипа не шифрован**: ключ устройства, пароль Wi-Fi и код привязки
  читаются при физическом доступе к UART. Серийная сборка `esp32s3_prod`
  отказывается работать без flash encryption, а порядок прожига eFuse описан в
  [`09-production-security.md`](./09-production-security.md).
* **BLE-линк не аутентифицирован** (Just Works): MITM может мешать привязке
  (DoS), но не расшифровать кадр версии 2 и не подменить grant — подпись
  проверяется на устройстве.
* **Непрерывный захват.** Пока колонка на связи и микрофон не выключен, звук
  уходит на сервер непрерывно (VAD решает, что считать репликой). Выключение
  микрофона останавливает захват в прошивке и отбрасывается сервером, но
  «пауза прослушивания» в интерфейсе должна быть видимой — красная лента
  перекрывает любое состояние.

## Проверено на железе

| Что | Результат |
|---|---|
| ключ P-256 создаётся и переживает перезагрузку | да, тот же открытый ключ после рестарта |
| самопроверка ECDH → HKDF → AES-GCM на устройстве | проходит (`[crypto] самопроверка привязки: ок`) |
| серверная подпись grant | **проверена сквозным тестом**: подпись, сделанная независимой реализацией (Python) по той же канонической строке, принимается; подпись чужим ключом отвергается |
| шифрование кадра | ECDH → HKDF → AES-256-GCM: ключи на обеих сторонах совпали байт в байт |
| отказ при неверном challenge/ключе/адресе | отвергается до применения настроек |
| BLE-реклама с сервисом `6b1f0001-…` | видна сканером, `local_name = DED-SPK-F904` |
| окно привязки закрывается по таймауту | 5 минут, дальше устройство невидимо |

## Что нужно от сайта

Модуль `speaker-pairing` в фронтенде:

1. ввод/скан кода → `pair/claim`;
2. `navigator.bluetooth.requestDevice({filters:[{services:[SERVICE_UUID]}],
   optionalServices:[SERVICE_UUID]})`;
3. чтение `info`, сверка ключа с серверным;
4. WebCrypto: `generateKey(ECDH P-256)` → `deriveBits` → `HKDF` → `AES-GCM`;
5. запись кадра частями, ожидание `notify` со `stage: "paired"`;
6. экран «Готово» с предложением назвать колонку и выбрать комнату.

Всё это — примерно 200 строк TypeScript и ни одной новой зависимости.
